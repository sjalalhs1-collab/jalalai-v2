# JalalAI v1.6 — Production Agent Runtime

## What changed
- Durable local job queue with bounded worker concurrency.
- Recovery of interrupted `running` jobs after process restart.
- Bounded job retries (1–5 attempts, default 3).
- Persistent runtime job state and queue.
- Human approval state for jobs submitted with `requireApproval: true`.
- Runtime job inventory/statistics and cancellation APIs.
- Optional Playwright-based browser automation adapter. Playwright is deliberately optional; the core package remains dependency-light.
- Existing v1.5 Knowledge Fabric, autonomous tools, workflows, research, verification, RAG, multi-provider routing and streaming are retained.

## Runtime API
- `GET /v1/runtime/jobs`
- `GET /v1/runtime/approvals`
- `DELETE /v1/runtime/jobs/:id`
- `POST /v1/runtime/jobs/:id/approve`
- `POST /v1/runtime/jobs/:id/reject`

Task submission additionally accepts:
- `async=true`
- `requireApproval=true`
- `maxAttempts` (bounded to 1–5)

Environment:
- `JALALAI_RUNTIME_PATH` — runtime state file (default `./data/jalalai-runtime.json`)
- `JALALAI_WORKERS` — worker concurrency (bounded 1–16, default 4)

## Production boundary
The local JSON runtime is durable across normal process restarts but is not a distributed queue. For multi-instance production, replace the storage/queue layer with PostgreSQL/Redis or another transactional job system.

The optional browser adapter requires Playwright and should be isolated for hostile/untrusted browsing. The existing code sandbox is also not a complete OS security boundary; use containers/microVMs for untrusted code.
